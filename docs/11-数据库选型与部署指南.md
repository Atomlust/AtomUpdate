## 1. 决策矩阵

两条产品形态共用同一套代码，部署时通过配置选择数据库，不做运行时切换。

| 维度 | SQLite（轻量，零配置默认，已实现） | PostgreSQL（生产建议，已实现） |
|---|---|---|
| 适用场景 | 单机 / 小团队 / 边缘设备（工控机、NAS、演示环境） | 多实例 / 高并发 / 生产环境 |
| 外部依赖 | 零（数据库文件随应用落盘） | 独立数据库服务（compose 内 `postgres:16-alpine`） |
| 实例数 | **1**（文件被单进程独占，不可水平扩展） | 1..N（Api 无状态，数据库共享） |
| 日志写入量参考 | 日增 ≤ 100 万行（保留 7 天 ≤ 700 万行，三类日志合计） | 无实际约束（分批删除兜底，可另接分区/表空间） |
| 并发写 | 单写者：写操作串行排队，`busy_timeout` 内等待；批量落库吞吐约数千行/秒（WAL 模式） | 多连接并发写，M6 压测 `/api/check` RPS ≈ 260 时 P95 ≈ 13ms（docs/internal/perf） |
| 全文/复杂查询 | 弱（无 jsonb，数组列退化为 JSON 文本） | 强（jsonb、数组、ctid 批删等已用上） |
| 备份 | 文件级复制（见 §3.5） | `pg_dump` / 数据卷打包（docs/09 §3） |
| 升级/迁移 | EF 迁移同样适用，但迁移集独立（见 §3.2） | 现有 `Data/Migrations` 直接沿用 |

经验法则：客户端数 ≤ 1 万、且只跑一个 web 实例、且不需要 PostgreSQL 运维能力 → 可选 SQLite；其余一律 PostgreSQL。SQLite 形态的主要价值是**零依赖**（一条 `docker run` 或直接 `dotnet run` 即可起服务），而非性能。

## 2. 现状：PostgreSQL 已实现

SQLite 化改造前，代码与 Npgsql 的耦合点共四处（下表为改造前快照，均已按 §3.6 消除）：

连接串来源：默认不在 `appsettings.json` 中，由部署环境注入（docker-compose `ConnectionStrings__Postgres`，docs/09 §2）；`Database:MigrateOnStartup=true` 时启动自动执行迁移。

### 主键生成：应用侧发号（SQLite 天然兼容的关键）

主键不依赖数据库自增：所有 `long Id` 经 `Data/IdGenValueGenerator.cs`（IdGen 雪花 ID，`Add` 时应用侧赋值，无数据库往返）生成，DbContext 中以 `SetValueGeneratorFactory` 全局挂接，并显式关闭 Npgsql IDENTITY 约定；发号器编号由 `IdGen:GeneratorId` 配置（多实例须互异，docs/09 §2）。这意味着**数据库层无 IDENTITY/AUTOINCREMENT 语义依赖，SQLite 兼容性不受主键方案影响**。

### 写路径压力参数（当前值）

| 路径 | 实现 | 当前参数 |
|---|---|---|
| 检查日志 | `Telemetry/CheckLogQueue.cs`（有界 Channel，满则丢最新并告警）+ `CheckLogWriterService.cs` 批量落库 | 队列 10,000；批量 200 条/事务 |
| 下载上报 | `Telemetry/ReportQueue.cs` + `ReportWriterService.cs`，同上 | 队列 10,000；批量 200 条/事务 |

以上参数目前均为代码内 `const`，不可配置——SQLite 化改造时是主要调整对象（见 §3.4）。

## 3. SQLite 支持方案（已实现；§3.1–§3.5 为设计稿原文，实现差异见 §3.6）

### 3.1 Provider 配置分支

新增配置键 `Database:Provider`（取值 `postgres`（默认）/ `sqlite`），连接串分别取 `ConnectionStrings:Postgres` / `ConnectionStrings:Sqlite`：

```csharp
// AtomUpdateApiHosting.cs（示意）
var provider = configuration.GetValue("Database:Provider", "postgres");
var connectionString = provider == "sqlite"
    ? configuration.GetConnectionString("Sqlite") ?? throw ...("缺少配置 ConnectionStrings:Sqlite")
    : configuration.GetConnectionString("Postgres") ?? throw ...("缺少配置 ConnectionStrings:Postgres");
services.AddDbContext<AtomUpdateDbContext>(options =>
    _ = provider == "sqlite" ? options.UseSqlite(connectionString) : options.UseNpgsql(connectionString));
```

设计工厂 `AtomUpdateDbContextFactory` 同步支持 `--provider` 参数（`dotnet ef migrations add X -- --provider sqlite`），用于分别生成两套迁移。`docker-compose.yml` 可另加一个可选 profile（省去 postgres 服务，`Database__Provider=sqlite` + 数据卷挂 `/data/atomupdate.db`）。

### 3.2 独立迁移集策略

EF 迁移是与 provider 绑定的（生成的 SQL、列类型注解均不同），两种 provider **各自维护一套迁移**，不做共享：

- 现有 `Data/Migrations/` 整体更名为 `Data/Migrations.Postgres/`（已上线环境的 `__EFMigrationsHistory` 不受影响，程序集内命名空间变更即可）。
- 新增 `Data/Migrations.Sqlite/`，仅含 InitialCreate（及后续差异迁移）。
- 运行时按 `Database:Provider` 选择 `MigrationsAssembly` / 迁移命名空间（`MigrateAsync(migrationsAssembly)` 或 `UseSqlite(conn, b => b.MigrationsAssembly(...))`）。
- CI / 开发流程：生成新迁移时**分别**对两个 provider 各跑一次 `dotnet ef migrations add`，两套成对提交（在贡献文档中注明）。

### 3.3 类型映射差异表

DbContext 中仅三处 provider 专有建模，处理方式：

| 现状（Npgsql） | 实体 | SQLite 方案 | 改动方式 |
|---|---|---|---|
| `timestamptz`（`timestamp with time zone`） | 全部 `DateTimeOffset` 属性 | `TEXT` ISO8601（EF Sqlite 默认映射） | 无需显式改动；沿用"时间统一 UTC 存储"约定（docs/03 §5），写入前必须 `UtcDateTime` 归一，避免 SQLite 无法比较混合偏移 |
| `jsonb`（`AuditLog.Details`） | `AuditLog.Details`（string） | `TEXT` | `HasColumnType` 条件化：pg → `jsonb`，sqlite → `TEXT`；代价是 SQLite 侧失去 jsonb 运算符（审计详情仅展示，无查询依赖，可接受） |
| `text[]`（`ReleaseNote.New/Improvements/Fixes/Notes`） | `List<string>` | `TEXT`（JSON 数组字符串） | 加 `HasConversion(List<string> ↔ JSON string)` 值转换器（两 provider 通用），或按 provider 条件映射 |
| `NpgsqlValueGenerationStrategy.None` | 所有 long Id | 无对应概念 | 包在 `if (provider == postgres)` 分支内（SQLite 下本就无 IDENTITY 约定，IdGen 发号不变，§2） |

另有一处隐式差异：`UpdatePolicy` / `ReleaseAsset` / `InstallationReport` 三个唯一索引建了 `AreNullsDistinct(false)`（pg 渲染 `NULLS NOT DISTINCT`，保证含 NULL 列的幂等去重）。SQLite 唯一索引恒为 NULLS DISTINCT，**含 NULL 列（如 `FromVersion`、`ErrorCode`）的重复行不会被索引拦截**，安装上报幂等语义弱化。缓解：为相关可空列配置值转换器（null → `""` 哨兵值落库）或应用层补偿校验；实施时须验证 `/api/report/install` 重复上报在 SQLite 下仍返回 `Duplicate=true`。

### 3.4 WAL 模式与写路径参数

SQLite 单写者约束下，连接串与 PRAGMA 建议（Microsoft.Data.Sqlite 连接串 `Default Timeout` 对应 busy 等待秒数）：

```csharp
// 连接打开后执行一次（可经 DataSourceSeeder 或 connstring 前置）
PRAGMA journal_mode = WAL;        -- 读写并发：写不阻塞读
PRAGMA busy_timeout = 5000;       -- 写锁等待上限 ms，须大于最长写事务
PRAGMA synchronous = NORMAL;      -- WAL 下安全且快
PRAGMA foreign_keys = ON;
```

配套参数建议（均为代码 `const`，改造时一并改为配置项）：

| 参数 | 当前（pg） | SQLite 建议 | 理由 |
|---|---|---|---|
| 日志批量落库 BatchSize | 200 | 200~500（保持 200 起步） | 单事务内行数越大锁持越久；WAL 下 200 行/事务远低于瓶颈 |
| 队列容量 | 10,000 | 不变 | 内存队列与 DB 无关 |
| 保留清理批次 | 5,000 | **1,000** | `ExecuteDelete` 大批删除易与批量写入争锁；`Take`+`ExecuteDeleteAsync` 在 Sqlite provider 的翻译（子查询 + LIMIT）需实测验证，必要时改为按主键子查询分批 |
| `Logging:RetentionDays` | 7 | 7（磁盘紧张时下调） | 日志三表是 SQLite 库的主要体积来源 |

### 3.5 已知限制

- **单写者**：所有写操作串行（WAL 缓解读写并发，不缓解写写并发）；写高峰时靠 `busy_timeout` 排队，超时即报错。
- **不可多实例共享文件**：SQLite 库文件不能被两个进程同时读写（网络文件系统上更不可行）。SQLite 形态固定单实例部署，与"服务端无状态可水平扩展"（docs/README）互斥——多实例需求出现时切回 PostgreSQL。
- **备份差异**：不能 `pg_dump`；在线备份用 `VACUUM INTO 'backup.db'` 或文件复制 + `PRAGMA wal_checkpoint(TRUNCATE)` 停顿窗口，避免复制到写入中途的文件。仍需与 `uploads` 卷（docs/09 §3）一起备份。
- **幂等去重弱化**：见 §3.3 唯一索引 NULLS 语义差异。
- **无 jsonb / 数组类型**：审计详情与版本说明四列退化为文本，相关分析能力下降（当前无此依赖）。

### 3.6 实现记录（2026-10-10，与设计稿的差异）

| 项 | 设计稿 | 实际实现 | 理由 |
|---|---|---|---|
| Provider 键值 | `postgres` / `sqlite` | `npgsql` / `sqlite`（零配置默认，2026-10-10 起由 npgsql 切换），`Data/DatabaseProviders.cs` 统一解析、装配与连接串解析，非法值启动即失败 | 与 EF 包/提供方命名对齐 |
| 迁移集隔离 | `Migrations/` 更名 + 运行时切 `MigrationsAssembly` | pg 迁移目录与命名空间**零变更**；新增派生上下文 `SqliteAtomUpdateDbContext`（同程序集），EF 迁移发现按 `[DbContext]` 特性过滤，两套迁移集天然隔离 | 不触碰已上线环境的 `__EFMigrationsHistory`，pg 侧无任何迁移动作 |
| DateTimeOffset | `TEXT` ISO8601 | **INTEGER（UTC Ticks，long）**：`SqliteDateTimeOffsetUtcTicksConverter` 全模型应用 | EF SQLite provider 无法翻译 DateTimeOffset 的 SQL 比较/排序（清理 `WHERE CheckedAt < cutoff`、统计 `>= since` 直接抛翻译异常）；整数比较即时间先后，写入前统一归一 UTC；可空属性由 EF 在转换器外直通 null |
| `text[]` 四列 | 显式 JSON 值转换器 | 无需显式转换器：EF primitive collection 约定自动将 `List<string>` 映射为 TEXT（JSON），读回自动还原 | EF 10 内建行为 |
| 幂等哨兵 | null → `""` 哨兵值 | **应用层补偿校验**：`ReportEndpoints` 安装上报插入前先查重，重复仍返回 `Duplicate=true` | EF Core 10 将 `convertsNulls` 转换器构造标记为内部 API（EF1001），TreatWarningsAsErrors 下不可用 |
| 检索大小写不敏感 | （设计稿未涉及） | 按 provider 分支：npgsql→`ILike`，SQLite→`Like`（ASCII 默认不区分大小写，行为对齐） | SQLite provider 无 `ILike` 翻译，不分支则用户/应用/版本/洞察搜索端点 500 |
| 保留清理 | sqlite 批 1,000，必要时按主键两步删 | 同批 1,000（`SqliteBatchSize`）；`Take`+`ExecuteDeleteAsync` **单语句**翻译实测通过（`DELETE ... WHERE Id IN (SELECT ... LIMIT n)`），两 provider 统一代码路径 | 单语句分批防长事务，无需两步删 |
| PRAGMA | 连接串前置 / Seeder 执行 | `DbConnectionInterceptor`（`SqliteConnectionPragmasInterceptor`）：连接打开时执行 `journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`、`foreign_keys=ON` | 对所有连接生效，免改连接串 |

两套迁移的生成命令（贡献新迁移时**分别**执行、成对提交）：

```bash
# PostgreSQL（默认上下文）
dotnet-ef migrations add X --project src/AtomUpdate.Api --startup-project src/AtomUpdate.Api

# SQLite（派生上下文 + 独立输出目录）
dotnet-ef migrations add X --project src/AtomUpdate.Api --startup-project src/AtomUpdate.Api \
  --context SqliteAtomUpdateDbContext --output-dir Data/Migrations/Sqlite \
  --namespace AtomUpdate.Api.Data.SqliteMigrations
```

测试矩阵：现有 363 项测试全部继续走 PostgreSQL（Testcontainers）；新增 `SqliteSmokeTests` 5 项（临时文件库，`DisableParallelization` 集合）覆盖启动迁移 + WAL PRAGMA、check 全路径、manage CRUD（JSON 列回读）、安装上报幂等、保留清理。全套 368 项 `dotnet test -m:1` 顺序执行全绿。
