# 11 数据库选型与部署指南

> **状态：SQLite 与 PostgreSQL 双 provider 均已实现。代码零配置默认 `Database:Provider=sqlite`，生产多实例/高并发切 `npgsql`；两套独立迁移集、启动 PRAGMA、类型映射、查询/清理兼容全部就位。compose 默认形态 `web` 为 SQLite 轻量单容器，PostgreSQL 为 `--profile postgres` 生产形态（`web-pg`）。部署步骤（compose、环境变量、备份、拓扑）见 [09 部署手册](09-部署手册.md)，本文只讲选型与数据访问实现，不重复部署操作。**
> 需求出处：[01 需求分析](01-需求分析.md)、[02 总体架构设计](02-总体架构设计.md) 部署形态、[03 数据模型与 API 设计](03-数据模型与API设计.md) §5。

## 1. 决策矩阵

两条产品形态共用同一套代码，部署时通过配置选择数据库，不做运行时切换。

| 维度 | SQLite（轻量，零配置默认） | PostgreSQL（生产建议） |
|---|---|---|
| 适用场景 | 单机 / 小团队 / 边缘设备（工控机、NAS、演示环境） | 多实例 / 高并发 / 生产环境 |
| 外部依赖 | 零（数据库文件随应用落盘） | 独立数据库服务（compose 内 `postgres:16-alpine`） |
| 实例数 | **1**（文件被单进程独占，不可水平扩展） | 1..N（Api 无状态，数据库共享） |
| 日志写入量参考 | 日增 ≤ 100 万行（保留 7 天 ≤ 700 万行，三类日志合计） | 无实际约束（分批删除兜底，可另接分区/表空间） |
| 并发写 | 单写者：写操作串行排队，`busy_timeout` 内等待；批量落库吞吐约数千行/秒（WAL 模式） | 多连接并发写；实测 `/api/check` RPS ≈ 260 时 P95 ≈ 13ms |
| 全文/复杂查询 | 弱（无 jsonb，数组列退化为 JSON 文本） | 强（jsonb、数组、ctid 批删等已用上） |
| 备份 | 文件级复制（见 §3.5） | `pg_dump` / 数据卷打包（docs/09 §3） |
| 升级/迁移 | EF 迁移同样适用，但迁移集独立（见 §3.2） | 现有 `Data/Migrations` 直接沿用 |

经验法则：客户端数 ≤ 1 万、且只跑一个 web 实例、且不需要 PostgreSQL 运维能力 → 可选 SQLite；其余一律 PostgreSQL。SQLite 形态的主要价值是**零依赖**（一条 `docker run` 或直接 `dotnet run` 即可起服务），而非性能。

## 2. 数据访问实现要点

### 主键生成：应用侧发号（SQLite 天然兼容的关键）

主键不依赖数据库自增：所有 `long Id` 经 `Data/IdGenValueGenerator.cs`（IdGen 雪花 ID，`Add` 时应用侧赋值，无数据库往返）生成，DbContext 中以 `SetValueGeneratorFactory` 全局挂接，并显式关闭 Npgsql IDENTITY 约定；发号器编号由 `IdGen:GeneratorId` 配置（代码默认 0，compose 内设 1，多实例须互异，docs/09 §2）。这意味着**数据库层无 IDENTITY/AUTOINCREMENT 语义依赖，SQLite 兼容性不受主键方案影响**。

### 写路径压力参数

| 路径 | 实现 | 参数 |
|---|---|---|
| 检查日志 | `Telemetry/CheckLogQueue.cs`（有界 Channel，满则丢最新并告警）+ `CheckLogWriterService.cs` 批量落库 | 队列 10,000；批量 200 条/事务（代码 const） |
| 下载上报 | `Telemetry/ReportQueue.cs` + `ReportWriterService.cs`，同上 | 队列 10,000；批量 200 条/事务（代码 const） |
| 安装上报 / Installation upsert | `Endpoints/Reports/ReportEndpoints.cs` 同步插入（插入前查重去重 / 并发冲突放弃） | 每请求一个小事务，QPS 低 |
| 保留清理 | `Telemetry/LogRetentionCleanupService.cs` 每 6 小时一轮，`Take(N)` + `ExecuteDeleteAsync` 循环分批删 | 批次 5000（pg）/ 1000（sqlite，`SqliteBatchSize`）；保留天数经 Settings 表可配（见下） |

队列容量、批量条数、清理批次为代码内 `const`；**日志保留天数与每应用检测记录上限**不是配置键，而是存 `Settings` 表（`logging.retention_days` 默认 7、`logging.check_log_per_app_limit`），由平台管理员在「管理后台 → 系统设置」读写，DB 有值优先、代码默认兜底，保存即时生效（docs/03、docs/09 §2）。

## 3. 双 Provider 实现

Provider 解析、装配、连接串解析统一收敛在 `Data/DatabaseProviders.cs`，两 provider 的差异全部按类型分支处理。

### 3.1 Provider 配置分支

配置键 `Database:Provider` 取值 `npgsql` | `sqlite`（**默认 `sqlite`**，与 EF 提供方命名对齐），非法值启动即失败。连接串解析：

- `npgsql`：取 `ConnectionStrings:Postgres`，缺失即启动失败（由部署环境注入，docker-compose `ConnectionStrings__Postgres`，docs/09 §2）。
- `sqlite`：走零配置默认——`ConnectionStrings:Sqlite` 显式配置优先；未配置时由 `ResolveSqliteConnectionString` 按 `/data` 目录存在性解析（存在 → `/data/atomupdate.db`，否则应用根目录 `atomupdate.db`）。appsettings 不内置 Sqlite 连接串默认值，保证零配置状态真实可达。

装配：`AddDbContext` 按 provider 调 `UseSqlite` / `UseNpgsql`；sqlite 模式附加连接打开 PRAGMA 拦截器（§3.4）。

### 3.2 独立迁移集

EF 迁移与 provider 绑定（生成的 SQL、列类型注解均不同），两 provider 各维护一套迁移，不共享：

- pg 迁移目录与命名空间**零变更**（`Data/Migrations/`，不触碰已上线环境的 `__EFMigrationsHistory`）。
- 新增派生上下文 `Data/SqliteAtomUpdateDbContext.cs`（同程序集），SQLite 迁移置于 `Data/Migrations/Sqlite/`、命名空间 `AtomUpdate.Api.Data.SqliteMigrations`；EF 迁移发现按 `[DbContext]` 特性过滤，两套迁移集天然隔离。
- 运行时按 `Database:Provider` 选择上下文类型，迁移集随上下文隔离。

工程内注册了两个 `IDesignTimeDbContextFactory`，生成迁移时**必须显式选择上下文**，且两套成对提交：

```bash
# PostgreSQL（须显式 --context，否则两个设计工厂无法二选一）
dotnet-ef migrations add X --project src/AtomUpdate.Api --startup-project src/AtomUpdate.Api \
  --context AtomUpdateDbContext

# SQLite（派生上下文 + 独立输出目录）
dotnet-ef migrations add X --project src/AtomUpdate.Api --startup-project src/AtomUpdate.Api \
  --context SqliteAtomUpdateDbContext --output-dir Data/Migrations/Sqlite \
  --namespace AtomUpdate.Api.Data.SqliteMigrations
```

> 当前迁移数：pg 9 个（InitialCreate…AddSettingTable）、SQLite 2 个（InitialCreate、AddClientIpAndSettings）。

### 3.3 类型映射差异

DbContext 中 provider 专有建模的处理方式：

| 建模点 | 实体 | pg | SQLite | 实现 |
|---|---|---|---|---|
| `DateTimeOffset` | 全部时间属性 | `timestamptz` | **INTEGER（UTC Ticks，long）** | `SqliteDateTimeOffsetUtcTicksConverter` 全模型应用——EF SQLite provider 无法翻译 DateTimeOffset 的 SQL 比较/排序（清理 `WHERE CheckedAt < cutoff`、统计 `>= since` 会抛翻译异常），整数比较即时间先后，写入前统一归一 UTC；可空属性由 EF 在转换器外直通 null |
| `AuditLog.Details` | 审计详情 | `jsonb` | `TEXT` | `HasColumnType` 按 provider 条件化；SQLite 侧失去 jsonb 运算符（审计详情仅展示、无查询依赖，可接受） |
| `ReleaseNote.New/Improvements/Fixes/Notes` | 版本说明四列 | `text[]` | `TEXT`（JSON 数组） | 无需显式转换器：EF primitive collection 约定自动将 `List<string>` 映射为 TEXT(JSON)、读回自动还原 |
| `NpgsqlValueGenerationStrategy.None` | 所有 long Id | 关闭 IDENTITY | 无对应概念 | 包在 provider 分支内（SQLite 下本就无 IDENTITY 约定，IdGen 发号不变，§2） |
| 唯一索引 `AreNullsDistinct(false)` | `UpdatePolicy`/`ReleaseAsset`/`InstallationReport` | `NULLS NOT DISTINCT` | 恒 `NULLS DISTINCT` | 见下「幂等去重弱化」 |

**幂等去重弱化**：SQLite 唯一索引恒为 NULLS DISTINCT，含 NULL 列（如 `FromVersion`、`ErrorCode`）的重复行不被索引拦截。采用**应用层补偿校验**——`ReportEndpoints` 安装上报插入前先查重，重复仍返回 `Duplicate=true`（不用 null→`""` 哨兵转换器：EF Core 将 `convertsNulls` 转换器构造标记为内部 API，触发 EF1001，在 `TreatWarningsAsErrors` 下不可用）。

**检索大小写不敏感**：按 provider 分支——npgsql → `ILike`，SQLite → `Like`（ASCII 默认不区分大小写，行为对齐）；SQLite provider 无 `ILike` 翻译，不分支则用户/应用/版本/洞察搜索端点 500。

### 3.4 WAL 模式与写路径参数

SQLite 单写者约束下，由 `Data/SqliteConnectionPragmasInterceptor.cs`（`DbConnectionInterceptor`）在连接打开时统一执行 PRAGMA，对所有连接生效、免改连接串：

```sql
PRAGMA journal_mode = WAL;        -- 读写并发：写不阻塞读
PRAGMA busy_timeout = 5000;       -- 写锁等待上限 ms，须大于最长写事务
PRAGMA synchronous = NORMAL;      -- WAL 下安全且快
PRAGMA foreign_keys = ON;
```

清理批次 SQLite 侧降为 1,000（`SqliteBatchSize`，`ExecuteDelete` 大批删除易与批量写入争锁）；`Take`+`ExecuteDeleteAsync` 单语句翻译实测通过（`DELETE ... WHERE Id IN (SELECT ... LIMIT n)`），两 provider 统一代码路径。日志批量落库保持 200（WAL 下无争用，未做配置化）。

### 3.5 已知限制

- **单写者**：所有写操作串行（WAL 缓解读写并发，不缓解写写并发）；写高峰时靠 `busy_timeout` 排队，超时即报错。
- **不可多实例共享文件**：SQLite 库文件不能被两个进程同时读写（网络文件系统上更不可行）。SQLite 形态固定单实例部署，与"服务端无状态可水平扩展"（docs/README）互斥——多实例需求出现时切回 PostgreSQL。
- **备份差异**：不能 `pg_dump`；在线备份用 `VACUUM INTO 'backup.db'` 或文件复制 + `PRAGMA wal_checkpoint(TRUNCATE)` 停顿窗口，避免复制到写入中途的文件。仍需与 `uploads` 卷（docs/09 §3）一起备份。
- **幂等去重弱化**：见 §3.3，靠应用层补偿校验兜底。
- **无 jsonb / 数组类型**：审计详情与版本说明四列退化为文本，相关分析能力下降（当前无此依赖）。

## 4. PostgreSQL 已有优化（无需重复投入）

热路径复合索引已就位（`Releases (AppId, Status, VersionMajor/Minor/Patch)`、`UpdateCheckLogs (CheckedAt, AppId)`、`DownloadLogs (DownloadedAt, AppId)`，迁移 `AddHotPathIndexes`），配合三类运行日志 7 天保留、每 6 小时分批（≤5000）删除的保留策略；实测 `/api/check` P95 ≈ 13ms，距 200ms 预算余量约 14 倍。
