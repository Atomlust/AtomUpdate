# 05 打包工具与存储设计（AtomUpdate.Packager / Cli）

> 依据《Packager 需求说明》整理。
> 上传走服务端 API（见 §8~§10、§13）。

## 1. 定位与边界

跨平台桌面工具（Avalonia）+ CLI，覆盖"从发布目录到版本可被客户端检查到"的完整链路：生成完整包与增量包、经服务端 API 上传、推送版本元数据到 Api。

| 事项 | 负责方 |
|---|---|
| 生成完整包 / 增量包 / 上传（经服务端 API）/ 推送元数据 | **Packager** |
| 检查更新 / 下载 / 安装 | 客户端侧 |
| 提供客户端下载 | 服务端 StorageRoot（`/uploads` 静态分发，`Storage:Root` 配置） |
| 打包工具鉴权 | 邮箱/密码登录换取 JWT（与管理后台同源账号） |

核心原则：一套工具覆盖完整发布链路；支持多种包格式；包文件经服务端上传端点落盘（Packager 不直连对象存储、不保存任何存储凭据）；鉴权为登录 JWT；同时支持 GUI（手动发布）与 CLI（CI/CD）。

## 2. 技术栈

| 类别 | 选型 |
|---|---|
| 框架 / UI | .NET 11 / Avalonia 12 |
| MVVM | CommunityToolkit.Mvvm |
| HTTP | 手写 `HttpClient` |
| 压缩 / 增量 | System.IO.Compression / 自研文件级（MVP）、bsdiff（二阶段） |
| CLI | 零依赖手写解析器 `CliParser` |

> 实际落地：Avalonia **12.1.4** / CommunityToolkit.Mvvm 8.4.2。未引入 Serilog、Refit、FluentValidation、M.E.DI、System.CommandLine——错误分类走 `PackagerException` 错误码、HTTP 为手写 `HttpClient`、表单校验内联在 ViewModel/CLI 层、命令解析为手写 `CliParser`（见 §13 注记）。无第三方存储 SDK 依赖（上传走服务端 API）。

## 3. 功能清单

| 模块 | 功能 |
|---|---|
| 登录与服务器配置 | API 地址 / 邮箱 + 密码登录（JWT）/ 连接校验 |
| 发布配置 | 项目 / 应用（**选定应用即选定平台**，平台只读显示）/ 架构（x64/x86/arm64，每个包一个）/ 通道（枚举：dev/preview/beta/rc/stable） |
| 打包 | 发布目录或已有安装包、版本号手填、完整包 zip、Windows 安装器（Inno Setup exe）、增量包 |
| 更新日志 | 新增/优化/修复/注意，Markdown，多语言 |
| 上传 | 经服务端上传端点（multipart）上传完整/增量包，服务端返回 URL 与 SHA-256 |
| 推送 | 构造元数据、保存草稿 / 直接发布 |
| 版本管理 | 历史列表、删除草稿（撤回/回滚为服务端能力，Packager 未接入） |
| CLI | 无 GUI 环境、CI/CD、脚本化发布 |

## 4. UI 结构（Avalonia）

- 主窗口：**单窗口四步向导**（无侧边栏）。①登录与项目/应用（邮箱/密码登录换取 JWT 后选择项目/应用，目标自动填充、平台只读带出；通道）→ ②版本与包（版本号手填/构建号/包来源/包类型/包架构/增量开关）→ ③更新日志（四类多行输入）→ ④发布设置（状态 draft/prerelease、强制更新、最低支持版本）。底部导航：[上一步] [下一步]（末步显示 [执行]），运行中显示 [取消]；[执行] 触发确认浮层（二次确认），确认后后台运行 `PublishOrchestrator`，进度经 `IProgress` 回 UI 线程、取消在阶段边界生效。向导步骤切换时草稿自动保存。
- 对话框：选择目录 / 选择文件 / 确认发布（浮层二次确认）/ 错误详情（错误码+消息+堆栈，可复制）。
- 主题：亮/暗色，中英文（`Loc` 本地化扩展）；表单校验内联在 ViewModel，错误显示为步骤底部提示行。
- 长任务（打包/上传/编译）可取消，进度经 IProgress 上报。

## 5. 核心流程

```
完整发布：登录（邮箱/密码 → JWT）→ ①选择项目/应用（目标自动填充）→ ②版本与包 → ③更新日志 → ④发布设置
  → 打包 → （可选）增量包 → 上传（服务端 API，返回 URL/SHA-256）→ 构造元数据 → 推送 Api → （可选）发布
仅打包：选包来源 → 打包 → （可选）增量 → 保存本地
仅上传：登录 → 选已有包（可多值）→ 上传服务端 → 返回 URL/SHA-256
```

## 6. 包格式与生成

| 类型 | 生成方式 | MVP |
|---|---|---|
| zip | 打包发布目录（扫描 → 按配置过滤排除 → 压缩 → SHA256） | ✅ |
| exe | Inno Setup（.iss 模板 → ISCC.exe 编译 → 校验输出） | ✅ |
| msi | WiX 编译 | 二阶段 |
| dmg / pkg | hdiutil / pkgbuild | 三阶段 |
| AppImage / deb / rpm | AppImageTool / dpkg-deb / rpmbuild | 三阶段 |

**命名规范**：`{projectKey}-{appId}-{version}-{platform}-{arch}.{ext}`，如 `myapp-com.company.myapp-1.3.0-windows-x64.zip`（`platform` 段取所属应用的平台，仅用于文件名可读性与人工归档，非服务端字段）。

**包元数据**（打包结果 + 上传结果合并为 `ReleaseAssetInputData`，写入 release 创建请求）：

```json
{ "kind": "full", "arch": "x64", "packageType": "zip",
  "url": "https://.../uploads/com.company.myapp/1.3.0/myapp-com.company.myapp-1.3.0-windows-x64.zip",
  "size": 12345678, "sha256": "..." }
```

> `sha256` 由 **Packager 打包时本地计算**（`PackageResult.Sha256`），`url`/`size` 取自服务端上传返回（见 §9）；`signature`/`keyId` 不填充（字段保留可空，见 §8）。

## 7. 增量包生成（文件级）

```
1. 选择基线版本（上一个已发布版本，加载其包清单）
2. 扫描当前版本文件，逐文件比较哈希：
   新增/修改 → 加入增量包；删除 → 记入删除清单；未变 → 跳过
3. 生成增量 zip + 删除清单 + 清单文件
4. 计算 SHA256
```

**增量包结构**：

```
delta-1.2.3-to-1.3.0-x64.zip
  ├── files/            # 新增/修改的文件（保留相对路径）
  ├── delete.json       # ["old.dll", ...] 删除清单
  └── manifest.json     # { fromVersion, toVersion, files[{path,hash,size}], deleted[] }
```

> 命名 `delta-{fromVersion}-to-{toVersion}-{arch}.zip`（`PackageNameBuilder.BuildDelta`，arch 小写）。

- MVP 基线为上一个已发布版本，服务端包选择按 `fromVersion == currentVersion` 直连命中；跨版本策略（链式 1.0→1.1→1.2 / 累积任意旧版→最新）二阶段。
- 二进制差分（bsdiff/hdiffpatch）二阶段。

实现要点（`FileDeltaGenerator`）：delta zip 根固定 `manifest.json` + `delete.json` + `files/`，删除项在 manifest.deleted 与 delete.json **双写**（更新器取并集）；JSON 以 STJ Web 默认（camelCase）写出；新增/修改判定为相对路径（POSIX 斜杠）SHA256 差异，快照跳过符号链接并应用排除 glob。跨组件互认由 `Tests.Packager/DeltaInstallContractTests` 守护——**真实生成的 delta 包直接交给更新器 `ZipInstaller` 安装**，断言变更/新增落盘、删除清单生效、未变文件保留，并覆盖 fromVersion 不符 → VerificationFailed。

## 8. 签名（可选）

Packager 不提供包签名——发布产物不含签名输出，`PublishStage` 为 **打包→增量→上传→推送→发布**。

签名能力在体系内保留的部分：

- 服务端 `ReleaseAssetInput`/`ReleaseAsset` 的 `Signature`/`KeyId` 字段保留为可空，未签名时省略。
- 更新器 `PackageVerifier` 验签（RSA + SHA256 + PKCS#1 v1.5，签名内容 `sha256|version|platform|arch`，详见 04 文档 §4.13）保留；**元数据无签名时自动跳过验签**——"签名可选、默认不验"的模型不变（02 文档 §6.3）。
- 需要签名发布的部署可在 Packager 之外（管理后台/REST 直接写入签名字段）完成签名步骤。

## 9. 上传（服务端 API）

Packager 不直连第三方存储，包文件统一经服务端 Manage 端点上传落盘：

```
POST /api/manage/projects/{projectId}/apps/{appId}/upload?version={version}
Authorization: Bearer {JWT}
Content-Type: multipart/form-data（文件字段 file）
```

- 服务端将文件写入存储根（配置 `Storage:Root`，默认 `ContentRoot/uploads`）下的 `{root}/{appId}/{version}/{filename}`，并**同步计算 SHA-256**。
- 返回 `{ url, sha256, size, filename }`；`url` 为 `{scheme}://{host}/uploads/{appId}/{version}/{filename}` **绝对地址**（`/uploads` 由 Web 宿主静态分发，公开可下载，先于鉴权）。
- 上传失败最多 **3 次尝试**（`RetryExecutor`，指数退避 1s/2s/4s；仅网络错误与 5xx 视为瞬态重试，同路径覆盖写幂等）；文件名取 multipart 文件名（`Path.GetFileName`），appId 中的路径分隔符会被替换，防目录穿越。
- 客户端下载 URL 即资产元数据 `url`，服务端不再区分存储 Provider——02 §8 部署形态中的"本地存储适配"即此模式。

## 10. 登录

登录方式：邮箱 + 密码 → `POST /api/manage/auth/login` 换取 JWT（与管理后台同源账号），上传与版本推送均带 `Authorization: Bearer {JWT}`。CLI 凭据经 `--email/--password` 或环境变量 `ATOMUPDATE_PACKAGER_EMAIL` / `ATOMUPDATE_PACKAGER_PASSWORD` 提供（CI secrets 注入，不落盘、不落日志）。Packager 不保存任何存储凭据。

## 11. 与 AtomUpdate.Api 的交互

### 11.1 端点（上传走 Manage 端点，版本资源化路径）

```
POST /api/manage/auth/login                                       登录（邮箱/密码 → JWT）
POST /api/manage/projects/{projectId}/apps/{appId}/upload?version={v}  上传包文件（multipart，字段 file）
POST /api/projects/{projectId}/apps/{appId}/releases              创建版本（单请求合并创建，含全部资产）
POST /api/projects/{projectId}/apps/{appId}/releases/{id}/publish 发布
POST /api/projects/{projectId}/apps/{appId}/releases/{id}/unpublish 撤回
GET  /api/projects/{projectId}/apps/{appId}/releases              查询版本
```

> Packager 实际调用：login / upload / create / publish / list。版本生命周期的其余端点（`PATCH .../releases/{id}` 编辑草稿、`DELETE .../releases/{id}` 删除草稿）由管理后台使用，契约见 [03 §3.4](03-数据模型与API设计.md)。**无 rollback 端点**（回滚为二阶段规划）。

认证：`Authorization: Bearer {JWT}`（邮箱/密码登录换取，`list` 子命令同样走登录会话）。`projectId`/`appId` 为**数字 ID**（登录后由项目/应用列表选定，GUI 自动填充）。

### 11.2 创建版本请求

```json
{
  "version": "1.3.0", "buildNumber": 100,
  "forceUpdate": false, "minSupportedVersion": "1.0.0",
  "notes": { "language": "en", "new": [], "improvements": [], "fixes": [], "notes": [] },
  "assets": [
    { "kind": "full", "arch": "x64", "packageType": "zip", "url": "...", "size": 0, "sha256": "...", "signature": null, "keyId": null, "silentArgs": null, "installArgs": null, "sourceId": null },
    { "kind": "delta", "fromVersion": "1.2.3", "arch": "x64", "packageType": "zip", "url": "...", "size": 0, "sha256": "...", "signature": null, "keyId": null }
  ]
}
```

> 字段命名与必填项以 `docs/contracts/openapi.v1.json` 的 `ReleaseCreateRequest`/`ReleaseAssetInput` 为准；发布通道在 `publish` 端点勾选，创建请求不带 `channels`。**请求体不含 `platform`/`runtime`**：平台由 URL 里的 `{appId}` 所属应用决定（`App.Platform`），架构在每个资产的 `arch` 上。

Packager 不填充 `signature`/`keyId`（签名字段保留可空，见 §8）；资产 `url`/`size` 取自上传端点返回，`sha256` 为打包时本地计算（见 §6/§9）。

发布请求预留 `rollout.percentage` 灰度字段（三阶段实现；**当前冻结契约未含该字段**，MVP 不传输）。

> **跨平台发布**：平台是应用属性——**同一产品的多平台分发 = 同一项目下建多个应用（每个 appId 一个平台）**，而不是同一 appId 下多条平台版本。Packager 一次向导 / Cli 一次调用针对**单个应用（即单平台）+ 单架构**；同一应用内的多架构（x64 / arm64）作为**同一条版本下的多个资产**上传。多平台发布由 Cli 循环或多次执行完成，版本号一致性由 Packager 保证；服务端对同一 `(appId, version)` 的重复创建按幂等处理（同资产 200、异资产 409 `RELEASE_EXISTS`）。

### 11.3 失败处理

- 上传失败最多 3 次尝试（同路径覆盖写，幂等，见 §9）；尝试耗尽 → 提示重试，流程中断（CLI 退出码 5）。
- 上传成功但推送失败 → 保留已上传资产（服务端同路径覆盖写可安全重试），可重试推送；多架构部分成功 → 重跑仅补传缺失资产，已上传文件同路径覆盖不产生重复对象。

## 12. 配置与本地状态

Packager **无持久化配置文件**（无 settings.json）：API 地址、账号等在向导内会话输入、即用即弃；CLI 走命令行参数与环境变量回退（见 §13）。工作目录固定 `%LocalAppData%\atomupdate\packager\`（CLI 可用 `--work-dir` 覆盖），**不保存任何密钥**（登录口令不落盘、不落日志）。

| 数据 | 位置 |
|---|---|
| 草稿 | `{work}\drafts\draft-{guid}.json`（版本、日志、包信息，步骤切换自动保存、启动恢复最新一份） |

> `PackagerPaths` 只创建工作目录与 `drafts/` 两个目录；上传状态由服务端落盘并返回 URL/SHA-256，Packager 不维护上传记录与凭据文件。

## 13. CLI（atomupdate-packager）

```bash
# 打包并发布（一键；--platform 必填，仅用于包文件命名，服务端平台仍由 --app 所属应用决定）
atomupdate-packager publish --api-url http://update.example.com \
  --email ops@example.com --password "$ATOMUPDATE_PACKAGER_PASSWORD" \
  --project 1 --app 2 --project-key myapp --app-id com.company.myapp --platform windows \
  --arch x64 --arch arm64 --version 1.3.0 --source ./publish --type zip \
  --note-new "新增xxx" --note "修复xxx" \
  --channels stable --publish

# 仅打包 / 上传已有包 / 查询版本
atomupdate-packager pack    --project-key myapp --app-id com.company.myapp --platform windows \
  --version 1.3.0 --source ./publish --type zip --output ./dist
atomupdate-packager upload  --api-url http://update.example.com --email ops@example.com --password "$ATOMUPDATE_PACKAGER_PASSWORD" \
  --project 1 --app 2 --version 1.3.0 --file ./dist/app-1.3.0-windows-x64.zip --file ./dist/delta-1.2.3-to-1.3.0-x64.zip
# upload 输出：OK  {url}  sha256={sha}
atomupdate-packager list    --api-url http://update.example.com --email ops@example.com --password "$ATOMUPDATE_PACKAGER_PASSWORD" \
  --project 1 --app 2
```

- `publish`/`upload`/`list` 均以 `--email/--password` 登录换取 JWT（缺省回退环境变量 `ATOMUPDATE_PACKAGER_EMAIL` / `ATOMUPDATE_PACKAGER_PASSWORD`），上传与创建版本均走该会话（见 §9/§11）。
- `upload` 需要 `--project/--app`（数字 ID）+ `--version` + `--file`（可重复多值），逐个上传并输出 `OK {url} sha256={sha}`。
- `--project-key/--app-id`（kebab 字符串，用于包命名与展示）与 `--project/--app`（数字 ID，用于 API 路由）配套提供；均支持环境变量回退（见 §13 末注记）。
- `list` 子命令与 `publish`/`upload` 一致走 `--email/--password` 登录。

> **多架构必须一次发齐**：创建幂等键是 `(appId, version)`，同一版本的 x64/arm64 资产属于**同一条 Release**。因此多架构要在一次 publish 里以多个 `--arch`（内部构造多个 `assets[]` 元素）提交；先发了 x64 再单独发同版本 arm64 会命中"同键不同资产"→ **409 `RELEASE_EXISTS`**。跨平台仍是多次调用——但每次换一个 `--app`。

CI 集成（GitHub Actions）：secrets 注入 api-url 与登录邮箱/密码（`ATOMUPDATE_PACKAGER_EMAIL` / `ATOMUPDATE_PACKAGER_PASSWORD`），版本取 `github.ref_name`。

**CLI 退出码**：0 成功 / 1 参数错误 / 2 配置错误 / 3 打包失败 / 4 签名失败（保留编号占位）/ 5 上传失败 / 6 推送失败 / 7 发布失败 / 8 未知错误。

实现要点：CLI 未使用 System.CommandLine——零依赖手写解析器 `CliParser`（支持 `--key value` / `--key=value` / 可重复多值如多 `--arch`/多 `--file` / 布尔标志不吞下一 token / `-h,--help` / 未知选项与位置参数报错）。命令集即 publish/pack/upload/list 四个；退出码映射：参数 1、打包类（Pack*/Delta*）3、上传类 5、Api*/ReleaseExists 6、发布阶段（通道发布）7、未知 8——2（配置错误）与 4（签名，保留编号占位）未使用。API 连接参数支持环境变量回退：`ATOMUPDATE_PACKAGER_API_URL` / `_PROJECT` / `_APP` / `_EMAIL` / `_PASSWORD`（及 kebab 字符串的 `_PROJECT_KEY` / `_APP_ID` 组合）。CLI csproj 以 `PackAsTool` 打包为 dotnet tool（命令名 `atomupdate-packager`），CI pack job 产出 NuGet。

## 14. 错误处理与日志

- 分类：`PackagerException` + `PackagerErrorCodes` 错误码（打包 / 增量 / 上传 / 推送 / 发布）。
- 重试：上传、推送、发布均走 `RetryExecutor`（最多 3 次尝试，指数退避 1s/2s/4s）；仅网络错误与 5xx 视为瞬态重试，409 `RELEASE_EXISTS` 等冲突不重试（见 §9）。
- 部分成功：全量包成功但增量包生成失败 → **整个流程中断**（CLI 退出码 3），不"询问是否继续"；已上传文件同路径覆盖写，重跑安全。
- 日志：无 Serilog；错误以 `PackagerException`（错误码+消息+堆栈）在 GUI 错误详情对话框展示、CLI 写 stderr；脱敏：不记录登录口令与 JWT 令牌。

## 15. 模块划分与核心接口

```
AtomUpdate.Packager            # Avalonia GUI：Views / ViewModels / Models / Converters（引用 Cli，传递获得 Core）
AtomUpdate.Packager.Cli        # Commands / CliParser / Program（dotnet tool）
AtomUpdate.Packager.Core       # Packaging / Delta / Publishing / Api / Models / Storage / Credentials / Signing
```

| 类型 | 职责 |
|---|---|
| `IPackager` | `Supports(PackageType)` + `PackageAsync(PackageContext, CancellationToken)` → `PackageResult`（FileName/PackagePath/Size/Sha256）；实现 `ZipPackager`（全量）、`InnoPackager`（Windows exe），无 MsiPackager |
| `FileDeltaGenerator` | 具体类（非接口）：`GenerateAsync(DeltaContext)` → 增量 zip（files/ + delete.json + manifest.json）+ 本地 SHA256 |
| `IAtomUpdateApiClient` | 版本资源化端点：`CreateReleaseAsync` / `PublishReleaseAsync` / `ListReleasesAsync` / `UploadAssetAsync`（multipart 上传，返回 url/sha256/size/filename） |
| `ManageApiClient` | 登录与列表：`LoginAsync`（邮箱/密码 → JWT）/ `ListProjectsAsync` / `ListAppsAsync` / `ListLatestReleaseAsync`（增量基线） |


## 16. 目录结构与分发

```
安装目录：AtomUpdate.Packager.exe（双形态单可执行：命中 CLI 子命令名走 CliRunner，否则启动 Avalonia GUI）
用户数据：%LocalAppData%\atomupdate\packager\
  └── drafts\draft-{guid}.json    （无 settings.json；工作目录仅 drafts/ 一个子目录）
```

- 发布形式：单文件可执行——GUI self-contained（默认 win-x64，内含 CLI 全部程序集，双击即启动），CLI 框架依赖单文件；发布脚本产出 `dist/tools/{gui,cli}/`。
- 分发：GitHub Releases / 官网下载 / 内部 NuGet 源（CLI 另以 dotnet tool 打包，命令名 `atomupdate-packager`）。
- **自更新**：AtomUpdate 体系自举——Packager 以客户端角色接入自家 SDK/更新器，狗粮验证全链路，三阶段实现；不引入 Velopack。

实现要点：GUI 项目引用 CLI 项目（传递获得 Core）。本地数据目录 `PackagerPaths` 只建工作目录与 `drafts/` 子目录（见 §12）；向导草稿为 `drafts/draft-{guid}.json`（STJ Web + 缩进，步骤切换自动保存、启动按时间恢复最新一份），**不含任何密钥字段**（登录口令不落盘）。
