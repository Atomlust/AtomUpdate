## 2. 模块划分与依赖

| 模块 | 类型 | 依赖 | 交付形态 |
|---|---|---|---|
| AtomUpdate.Core | 类库 | 无 | NuGet（内部）/ 项目引用 |
| AtomUpdate.Abstractions | 类库 | Core | NuGet |
| AtomUpdate（SDK） | 类库 | Abstractions, Core, M.E.Configuration/DI/Hosting/Http/Logging/Options 抽象 | **NuGet `AtomUpdate`**（仅 net11.0） |
| AtomUpdate.Updater | 控制台/WinExe | 无（report 模型自带，JSON source-gen） | **Native AOT** 单文件 exe（6 RID，实测 win-x64 约 7.7MB/RID），NuGet 内嵌 + SDK 首次运行释放到版本化目录 |
| AtomUpdate.Api | ASP.NET Core | Abstractions, Core, Validation | 自托管 / Docker |
| AtomUpdate.Web | Blazor 宿主（全局 Auto 外壳：App.razor + Error 页） | Api, Web.Client（Core/Validation 经 Api 传递） | 单进程内合并托管 Api（`AddAtomUpdateApi` + `MapAtomUpdateApi`） |
| AtomUpdate.Web.Client | WASM（全局 Auto：Routes/布局/页面） | Core（**不引用 Validation**，客户端零使用） | - |
| AtomUpdate.Packager | Avalonia | Packager.Core（经 Cli 传递） | 跨平台桌面工具（GUI + 内置 Cli / dotnet tool），实际拆为 **Packager.Core / Packager.Cli（dotnet tool）/ Packager（Avalonia GUI）** 三项目；单一 exe 按 `argv[0]` 双形态分发（见 05 §13/§16） |
| AtomUpdate.Tests.* | 测试 | 各模块 | CI |

**依赖规则：**

1. `Abstractions` 层零运行时依赖（仅 BCL + Core），保证 SDK 体积与宿主隔离。
2. 主程序**不引用** Updater 项目本体；Updater 单文件二进制嵌入 NuGet 包，SDK **首次运行时释放到本地版本化目录**（`%LocalAppData%\AtomUpdate\updater\{version}\`，macOS/Linux 对应路径），版本化目录避免覆盖正在运行的更新器；可选独立分发（SDK 从服务端下载最新更新器）归二阶段。
3. `Core` 只放跨端契约：DTO（纯 POCO）、枚举、常量、错误码、协议版本号——**零依赖、零逻辑、零验证代码**。**SDK** 仅引用 Core，依赖面严格收敛，不引入验证依赖（NuGet 分发，体积敏感）；Packager（含内置 Cli）属本地工具，表单校验内联在 ViewModel（不引用 AtomUpdate.Validation 包，亦未引入 FluentValidation）。FluentValidation 规则独立为 `AtomUpdate.Validation`（引用 Core），**仅服务端 Api 使用**（Api 引用 Validation；Web 经 Api 传递，Web.Client **不引用**——Blazor Auto 全局模式下客户端零校验规则，服务端是校验权威）；SDK 等客户端只做轻量手写校验（必填/格式）；Updater 不引用 Core（AOT 要求 JSON source-gen 自建 report 模型，临时配置/状态文件为文档化格式）。
4. Web 进程内合并托管 Api：`Web/Program.cs` 调 `AddAtomUpdateApi` 装配、`MapAtomUpdateApi()` 映射端点，叠加 `MapRazorComponents`；Api 亦可独立宿主（`src/AtomUpdate.Api/Program.cs`，不含 Blazor），部署时可选择拆分。

## 3. 关键流程推演

### 3.1 更新检查（读路径，性能核心）

```
POST /api/check
  ① 解析请求（projectKey/appId/platform/arch/channel/currentVersion/policyVersion）
  ② 租户解析（公开端点：匿名按请求体 projectKey/appId 反查租户，JWT 会话按 tenant_id）
  ③ 平台守卫：request.platform == App.Platform → 不符 400 PLATFORM_MISMATCH
  ④ 查询发布缓存：
       key = (appId, channel)                       ← 与平台/架构无关，架构筛包在响应阶段
       → 最新已发布 Release + 其全部资产 + forceUpdate/minSupportedVersion + policyVersion
  ⑤ 架构筛包：按 request.arch 取可用资产（arm64 缺包回落 x64；一个都没有 → hasUpdate:false）
  ⑥ 版本比较：currentVersion < latestVersion（或降级策略开启时反向）？
       - 无更新 → 精简响应 { hasUpdate:false, latestVersion, policyUnchanged }
       - 有更新 → 组装完整响应（package 按 currentVersion 选增量/完整包 + releaseNotes + policy）
  ⑦ policyVersion 比对 → 相同则去掉 policy 体
  ⑧ 计算强 ETag 并写响应头（组成仍含 platform|arch）→ 异步写 UpdateCheckLog（命中 304 也记，ETagHit=true）
  ⑨ If-None-Match 命中 → 直接返回 304（无 body）
```

**性能设计：**
- ④ 的发布状态用**内存缓存**（`MemoryReleaseCache`/`MemoryReadCache`，TTL 由 `Cache:ReleaseTtlSeconds` 默认 30s 控制）；发布/撤回经 `Invalidate(appId)` bump epoch 即时失效，无需等 TTL。Redis 二级缓存归二阶段（当前未接入）。
- ⑧ 统计日志走 Channel + 后台批量写库，绝不阻塞检查路径。
- 无状态：实例间无粘性，天然水平扩展。

### 3.2 发布（写路径）

```
Packager 登录 JWT → POST /api/manage/projects/{projectId}/apps/{appId}/upload（multipart；服务端落盘
  Storage:Root 并同步计算 SHA-256，返回 url/sha256/size/filename）
  → POST /api/projects/{projectId}/apps/{appId}/releases（JWT；合并多架构 assets 单请求创建）
  → 服务端校验（FluentValidation：版本号格式、URL、SHA256 格式、通道枚举合法性）
  → 创建 Release(draft，应用内一条版本号一条记录) + ReleaseAsset(每条带 Arch)
  → 发布动作：状态 draft→published，bump 该 (app, channel) 的 release 序号
  → 缓存失效 → 下一次检查请求即看到新版本
```

### 3.3 更新安装（端侧核心，详见 04 文档）

```
SDK 前台/静默下载 → SHA256+签名校验（第一层；SHA256 强制，签名可配、默认不验，见 §6.3）→ ReadyToInstall
→ SDK 写临时配置 updater-{guid}.json + 启动 Updater.exe → 主程序退出
→ Updater 抢全局互斥锁（失败退出码 0x1001）
→ 参数校验（失败 0x1002）→ 校验包 SHA256/签名（失败 0x1004；SHA256 强制，签名按更新器自身配置）
→ dry-run（--dry-run 只校验与演练，即退出）→ 写 starting 状态
→ 自升级交接（需要时 Updater.New.exe --replace-old → 退出）→ 提权预判与自我提权（被拒 → 0x1003）
→ 等待主程序退出 → preInstall 钩子 → 备份 → 按 merge/replace 策略替换/运行安装器 → postInstall 钩子
→ 写终态状态文件（`state/{appId}/updater-state.json`）→ 直接回传 Api（失败则 SDK 启动时补报）
→ 重启主程序 --skip-update-check → 清理临时文件 → 退出（0x0000）
→ 失败：回滚备份 → 状态文件标记 failed → 主程序下次启动读取后补报
```

> 实际实现中，参数/包校验在自升级交接之前（避免用未校验的任务交接）；dry-run 是校验后即返回的门；SDK 侧签名校验只做"签名字段存在性"检查，真正的密码学验证发生在更新器安装层（见 §6.3）。

### 3.4 策略（policy）流转

```
管理端修改 UpdatePolicy → UpdatePolicyVersion+1（DB 事务内）
→ 客户端请求带 policyVersion → 服务端比对：
   相同 → policyUnchanged:true，无 policy 体
   不同 → 完整 policy 体，客户端落盘缓存（%LocalAppData%/AtomUpdate/cache/{appId}）
→ SDK 各子系统（轮询/下载/安装/通知）读运行时 policy，合并优先级见下。
```

配置优先级（低→高，SDK 侧五级，见 04 文档 §3.7）：代码默认值 → appsettings.json → 环境变量（`ATOMUPDATE_` 前缀）→ 代码 AddAtomUpdate 覆盖 → 服务端 policy（仅策略类字段，不能覆盖身份类字段）。

> 更新器侧采用独立分层（内置默认 → updater.default.json → --config → 环境变量 → 命令行），见 04 文档 §4.13。

## 4. 技术选型与论证

| 决策点 | 选型 | 理由 | 备选/风险 |
|---|---|---|---|
| API 框架 | ASP.NET Core 11 Minimal API | 与 Web 同栈、性能好、OpenAPI 内建 | Controller 风格亦可，按团队习惯 |
| ORM | EF Core 11 | 迁移工具链成熟 | Dapper（统计查询热路径可用） |
| ID 生成 | **IdGen 库**（RobIII/IdGen，Snowflake 风格 64 位 long） | 时间有序、趋势递增（主键索引友好）、分布式无中心、应用侧生成 | 自增序列（分布式需中心协调）；GUID（随机主键页分裂）；库无 EF/JSON 配套包，需少量胶水代码（ValueGenerator + JsonConverter） |
| 数据库 | SQLite（默认）/ PostgreSQL（生产） | SQLite 零配置轻量私有化；PostgreSQL 事务、JSONB（AuditLog.Details）、生态，多实例/高并发 | SQL Server |
| 缓存 | 内存缓存（Redis 规划中） | 单实例内存 + epoch bump 失效足够；多实例缓存一致性归二阶段 | Redis |
| 管理后台 | Blazor Auto + **AtomBlazor** | 需求锁定；Auto 兼顾首屏与交互 | Server 模式（内网部署更快）；Bootstrap/自研（失去现成 DataTable/Form/Dialog 组件层） |
| 表单验证 | FluentValidation | 规则独立为 AtomUpdate.Validation 包，仅服务端 Api 使用 | DataAnnotations |
| 桌面工具 | Avalonia 12 | 跨平台、MVVM、单代码库 | MAUI（Linux 不支持） |
| 签名 | **RSA + SHA256 + PKCS#1 v1.5** | 更新器零第三方依赖即可验签（`System.Security.Cryptography` 内置）、Native AOT 天然安全；签名可选，元数据无签名时自动跳过验签 | Ed25519（密钥短/无 Padding Oracle 类风险，但需第三方库且 AOT 兼容性未验证，未采用） |
| 增量 | **文件级增量 MVP**（Packager 生成 → SDK 增量优先选择 → 更新器应用 delete 清单）；跨版本策略与 bsdiff/hdiffpatch 二阶段 | 见 05 文档 §7 | - |
| 客户端通知 | 抽象 IUpdateNotifier，默认 Auto（Toast/Console 回落） | 无 UI 宿主回落 Console/日志 | - |

**.NET 11 目标框架策略：**
- 全解决方案统一 `net11.0`（SDK / Updater / Packager / Api / Web 均单目标，跨平台）。
- 当前无 `net11.0-windows` 附加目标，也无独立 `AtomUpdate.UI.*` 适配包；WPF/WinForms/MAUI 宿主直接引用 SDK（`AtomUpdate`）即可，UI 适配归二阶段。
- 全链路 `LangVersion=latest`，`Nullable=enable`，`TreatWarningsAsErrors=true`。

## 5. 解决方案结构（.slnx 布局）

```
AtomUpdate.slnx
├─ src/
│  ├─ AtomUpdate.Abstractions/           # SDK 接口（零运行时依赖，仅 BCL + Core）
│  ├─ AtomUpdate.Api/                    # REST 端点（可独立宿主，或被 Web 单进程合并托管）
│  ├─ AtomUpdate.Core/                   # 跨端契约：DTO + 枚举 + 常量 + 错误码（零依赖零逻辑）
│  ├─ AtomUpdate.Packager/               # Avalonia GUI（引用 Packager.Core）
│  ├─ AtomUpdate.Packager.Cli/           # dotnet tool（atomupdate-packager）
│  ├─ AtomUpdate.Packager.Core/          # 打包/上传/发布编排（被 GUI 与 Cli 共用）
│  ├─ AtomUpdate.Updater/                # 发布为 Native AOT single-file
│  ├─ AtomUpdate.Validation/             # FluentValidation 规则（仅 Api 引用）
│  ├─ AtomUpdate.Web/                    # Blazor 宿主（全局 Auto：App.razor 外壳 + Error 页；引用 Api + Web.Client）
│  ├─ AtomUpdate.Web.Client/             # WASM 页面程序集（全局 Auto：Routes/布局/页面；仅引用 Core）
│  └─ AtomUpdate/                        # SDK 实现（NuGet 包 AtomUpdate）
├─ samples/
│  └─ AtomUpdate.Sample.Console/         # SDK 接入样例
├─ tests/
│  ├─ AtomUpdate.Tests.Api/              # 集成测试（WebApplicationFactory + Testcontainers-PG + SQLite 冒烟）
│  ├─ AtomUpdate.Tests.Core/
│  ├─ AtomUpdate.Tests.Packager/
│  ├─ AtomUpdate.Tests.Sdk/
│  └─ AtomUpdate.Tests.Updater/
└─ docs/
```

NuGet 打包要点（AtomUpdate SDK 包）：
- 更新器二进制（按 RID 的 Native AOT 单文件）以 **NuGet 原生资产**（`runtimes/{rid}/native/`）嵌入 `AtomUpdate` 包；SDK 首次运行时按当前 RID/OS 释放对应更新器到版本化目录 `%LocalAppData%\AtomUpdate\updater\{version}\`（macOS/Linux 对应目录），并把版本号写入同级的 `updater/current` **指针文件**供后续启动解析（04 §5.2）。
- Updater 二进制按 `win-x64 / win-arm64 / osx-x64 / osx-arm64 / linux-x64 / linux-arm64` 六个 RID 预编译入包（Native AOT，win-x64 单文件约 7.7MB，六 RID 全内嵌约 +40MB；可按需拆分 RID 包减小主包体积）。包内布局固定为 `runtimes/{rid}/native/AtomUpdate.Updater[.exe]`（04 §5.2）。

### 5.1 管理后台前端结构（Web + Web.Client）

| 位置 | 职责 |
|---|---|
| `Web/Components/App.razor` | HTML 外壳，样式顺序固定：`_content/AtomBlazor/atomblazor.css`（Tailwind v4 基础层 + 组件类）→ `_content/AtomBlazor/css/themes.css`（**库定义主题令牌默认值**）→ `theme.css`（我们自写的令牌覆盖：黑/白中性 + 胶囊圆角，须晚于 themes.css 才能覆盖其 `:root` 默认值）→ `app.css`（业务类 `au-*`）。加载 `_content/AtomBlazor/js/theme-init.js`（`data-default-dark="false"`，首绘前应用已存主题、无则固定浅色，避免暗色闪屏）；`<ImportMap />` 必需（库的 select/dialog/portal 等 JS 模块按 importmap 解析） |
| `Web/wwwroot/theme.css` | 主题令牌覆盖（`--primary`/`--background`/`--sidebar*`/`--radius-*`/`--font-*`）——覆盖 AtomBlazor `themes.css` 的 `:root` 默认值 |
| `Web/wwwroot/app.css` | 全站业务样式表（`--au-*` 令牌 + 组件对齐基准 + 外壳/页面骨架类，前缀 `au-`）；因库全在 `@layer` 内，我们的无层规则天然优先，无需 `!important` |
| `Web.Client/Layout/MainLayout.razor` | 浅色 Sider（232 / 折叠 48）+ 56 顶栏（折叠入口 + 用户下拉）+ 页脚；登录态就绪前不渲染 `@Body` |
| `Web.Client/Layout/BareLayout.razor` | 登录页等无外壳布局 |
| `Web.Client/Components/PageContainer.razor` | 页面骨架：面包屑 + `h1` 标题 + 描述 + 右上 `Extra` 操作区 + `ChildContent` 内容区（宽度自适应，无上限） |
| `Web.Client/Components/OverviewStats.razor` | 概览指标卡片行（数据源 `GET /api/manage/overview`） |
| `Web.Client/Services/ReleaseScope.cs` | 版本发布作用域（projectId+appId）：集中生成 API 地址与子页面路由，列表↔子页面经查询串传递作用域 |
| `Web.Client/Services/NoteSections.cs` | 更新日志四段（新增/优化/修复/注意）录入约定：多行文本按行拆成 `ReleaseNote` 的四个字符串数组，行首 `- ` / `* ` 剥离，行内 Markdown 原样存储；四段全空时新建不下发 Notes |
| `Web.Client/Pages/*` | 设置向导（Setup）/ 登录 / 概览（Home）/ 项目 / 应用 / 版本发布 / 检查日志（CheckLogs）/ 统计（Stats）/ 系统设置（Settings）/ 审计日志 /（平台管理员）租户 / 用户；`NotFound.razor` 兼作状态码页 |
| `Web.Client/Pages/Release*.razor` | 版本发布拆为独立路由（不用弹窗）：`/releases`（列表）、`/releases/new`、`/releases/{ReleaseId:long}`（详情）、`/{id}/edit`、`/{id}/publish`、`/{id}/unpublish`；子页面靠 `?projectId=&appId=` 还原作用域。新建/编辑页的更新日志为**四段多行输入**（新增/优化/修复/注意，`.au-notes-grid`）；详情页按四段分组渲染；页头"新建草稿"按钮恒定可用，不依赖检索条件。**版本页面不出现平台选择**（平台是应用属性，子页面只读展示，经 `ReleaseScope.PlatformAsync` 取；架构只出现在包区）；列表页工具栏显示"平台 · 共 N 个版本（平台由应用决定，架构在各包上）"并带"包架构"列 |

查询区骨架：`.au-query`（flex + wrap）容纳 `.au-field` 检索字段与 `.au-field-actions` 按钮组，按钮组与检索条件同排（`align-items: flex-end` 底对齐，宽度约 800px 以上不换行）。**页头主操作按钮不得被检索态禁用**（检索归检索，新建归动作）。

主题基线：**黑/白中性主题**——主操作色 `#000`（`theme.css` 的 `--primary`）、胶囊按钮（`--au-radius-pill`，在 app.css 里覆盖库的 `rounded-md`）、灰底胶囊标签、卡片 12px + 1px 细线无阴影、浅灰发丝线分隔、控件 8px（库 `rounded-md` 即 `--radius-md: .5rem`，与 `--au-radius-control` 同值，免覆盖）。组件一律用 AtomBlazor，**业务侧不手写 Tailwind 类**（库自带编译后的 atomblazor.css，我们只用其组件 + 自己的 `au-*` 与令牌）；库无 ProLayout/ProTable，"页头 + 查询区 + 表格 + 行操作文字链"结构仍由 `PageContainer` + `au-*` 工具类实现。

DataTable 用法约束（换库踩坑，写死在页面里）：可空字段作列时必须收敛为空串（`Property="@(c => c.X ?? string.Empty)"`），否则库抛 `Column 'x' returned null for a non-nullable type.` 并终止电路；`InitialPageSize` 默认 **5**，且 `ShowPagination="false"` 仍会分页，服务端一次取全量的列表必须显式 `InitialPageSize="200"`。空状态文案 "No results found" 是库内硬编码英文，无本地化钩子。


## 6. 安全设计

### 6.1 威胁模型要点

| 威胁 | 缓解 |
|---|---|
| 包被篡改（传输/存储） | SHA256 校验（强制）+ RSA 签名（可选、默认不验；签名由发布方在发布元数据中注入，公钥随客户端内嵌分发） |
| 中间人替换 URL | HTTPS + 元数据由 API 下发（API 走 TLS；上传/推送走登录 JWT，检查/上报公开、包经 SHA256+签名校验兜底） |
| 重放/降级攻击 | 防降级由应用级策略 `AllowDowngrade` 控制（默认关）；签名覆盖版本号与包哈希 |
| 元数据伪造 | 管理 API 鉴权（登录 JWT），操作写 AuditLog；check/report 为公开只读/匿名统计端点 |
| 钩子脚本注入 | 钩子文件必须来自校验通过的包内（按清单相对路径核验），禁止接受外部路径参数执行任意命令（白名单后缀 + 相对路径约束） |
| 凭据泄露 | Packager 不保存任何存储凭据；登录口令仅经环境变量（CI secrets）或 GUI 会话输入提供，不落盘、不落日志 |
| 隐私 | 机器指纹为不可逆哈希（应用级盐 appId，见 04），统计可关闭 |

### 6.2 鉴权设计

| 端点类别 | 认证 |
|---|---|
| /api/check、/api/report、/api/stats | 公开（匿名按请求体 projectKey/appId 反查租户；JWT 会话按 tenant_id 过滤） |
| /api/manage/.../upload、/api/projects/.../releases | 登录 JWT（Packager 邮箱/密码登录，Manage 策略） |
| /api/manage | 用户 JWT（MVP 本地账号，预留 OIDC） |
| 角色模型 | MVP 简化为两级：平台管理员 + 租户内全权用户（细粒度角色与项目成员二阶段扩展） |

### 6.3 更新包签名方案

```
签名内容（发布方注入，可选）:
  signature = RSA.Sign(Utf8Bytes("{sha256}|{version}|{platform}|{arch}"), SHA256, Pkcs1)
      // sha256/platform/arch 统一小写、version 原样；platform 取自所属 App、arch 取自该资产自身
      // 签名输入的字段集合含平台与架构，防跨平台/跨架构资产替换
元数据: sha256, signature(_BASE64), keyId   // 均可空，发布时缺省省略
Updater 验签: 内置公钥集（keyId → PEM 公钥，仅随客户端内嵌，不从 Api 动态获取），支持密钥轮换（新旧公钥并存一个版本周期）；元数据无签名时自动跳过验签
SDK 验签: RequireSignature=true 只检查"包带签名"（SDK 侧公钥集分发归二阶段）；真正的密码学验证发生在更新器安装层
```

**签名可选：默认不验、要验才开。**

- 发布侧：Packager 不签名——`signature`/`keyId` 缺省省略，打包/上传/发布流程不受影响；需要签名的部署在 Packager 之外（管理后台/REST）写入签名字段。
- 客户端：`Verify.RequireSignature`（SDK）/ `verification.requireSignature`（更新器）默认 `false`；置 `true` 启用验签（需发布包已签名，否则校验失败——SDK 侧 `VerifyFailed`、更新器侧 0x1004）。**SHA256 校验始终强制、不可关闭。** 注意 SDK 侧当前只做"签名字段存在性"检查（见上），真正的密码学验证发生在更新器安装那一层。
- 开关仅来自客户端本地配置：**服务端策略不可覆盖**（校验开关不在策略下发字段内）。更新器侧开关仅从内置默认与安装目录 `updater.default.json` 读取，不经 SDK 临时配置/环境变量/命令行传递（防同机篡改降级）；SDK 侧开关走 04 文档 §3.7 的本地配置链（appsettings/环境变量/代码覆盖均可设置，服务端策略除外）。
- 风险声明：默认不验签时，服务端被攻破可下发未签名/被替换的恶意包直接通过校验；同机攻击者可改写下载包与临时配置中的 `sha256` 绕过完整性校验。需要防护此类攻击的部署应显式启用签名验证，并且**必须走更新器安装链路**（SDK 直装/仅下载场景暂无验签能力）。

## 7. 可观测性与运维

- API：OpenAPI（`/openapi/v1.json`）+ `/health` 探针；三类运行日志（检查/下载/安装）经有界 Channel 批量落库，后台「检查日志」「统计」页可查（默认 `Microsoft.Extensions.Logging`，生产日志级别降为 Warning）。Serilog 结构化日志与 Prometheus 指标暴露归二阶段，当前未接入。
- Updater：本地滚动日志（logPath 可配，保留天数可配）+ 状态文件（机器可读结果）。
- SDK：事件回调 + 本地诊断日志；上报失败静默丢弃不阻塞主程序（安装结果例外，落盘补报）。
- 审计：发布、权限变更、策略修改、撤回 全量记 AuditLog（MVP 已有基础查询页，全量维度报表与导出归二阶段）。

## 8. 部署形态

| 形态 | 组成 | 适用 |
|---|---|---|
| 单机私有化 | Api+Web 单进程 + SQLite（默认，零配置）+ 本地存储 | 小团队内网、边缘设备 |
| 容器化 | docker-compose：默认 `web` 一体镜像【Api+后台单进程，SQLite】；`--profile postgres` 起 `web-pg` + `postgres` 双容器 | 标准交付（详见 docs/09） |
| SaaS | Api 多实例（无状态）+ 托管 PostgreSQL + 对象存储 + CDN | 平台运营 |
